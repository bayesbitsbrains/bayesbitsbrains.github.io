# Kolmogorov Complexity

In the [previous chapter](08-coding_theory), we saw what coding theory tells us about compressing strings. If we treat letters of the text independently, coding theory is especially powerful. But that's an assumption that good compression algorithms can't make. 

Kolmogorov complexity is a different approach to the same compressing question. It's the ultimate limit for how much a file can be compressed. This makes it a very powerful theoretical concept to have in our dictionary!


{/*My favorite applications of Kolmogorov complexity are not practical ones, but a clean conceptual framework for discussing these ideas.*/} 

<KeyTakeaway>
Kolmogorov complexity of an object is the length of its shortest specification. This is the ultimate limit of compression. 
</KeyTakeaway>

## The Mandelbrot Set

Take a good look at the following picture.<Footnote>Be careful, though, excessive zooming may result in a psychedelic experience. </Footnote> It shows the Mandelbrot set—we color each pixel of the plane based on how quickly a certain sequence of numbers shoots to infinity.

<MandelbrotExplorer />

This is the gist of Kolmogorov complexity. For any given object—represented as a binary string—its Kolmogorov complexity is the length of the shortest program that prints that string. This is the limit on how much a file can be compressed. 

Here are a few more examples. 

- Although digits of <Math math="\pi" /> have many random-like properties, the Kolmogorov complexity of its first million digits is extremely small. That's because there are some [extremely short](https://cs.uwaterloo.ca/~alopez-o/math-faq/mathtext/node12.html) programs printing it. 
- Larger numbers (written down in binary) typically have larger Kolmogorov complexity. But there are huge numbers like <Math math = "3^{3^{3^{3^3}}}" /> with very small Kolmogorov complexity.  
- Whenever you can zip a file to a size of 100 MB, you can say that "Kolmogorov complexity of the file is at most 100 MB"
- If you flip a fair coin <Math math="n" /> times, the resulting sequence is likely to have Kolmogorov complexity of about <Math math="n" />. There's no good way of compressing it.  


And here's one more example: The final riddle we haven't discussed yet—[Hutter's challenge](00-riddles#wikipedia) is the challenge of upper bounding the Kolmogorov complexity of 1GB of Wikipedia as much as possible.

## Definition of Kolmogorov complexity

Kolmogorov complexity is a great concept that helps me think clearly about all kinds of things. The unfortunate part is that it takes a bit of time to get over some subtleties. The two main ones: How do we define it formally, and how do we compute it? 

<Expand headline = "Choosing the language">

Kolmogorov complexity of <Math math="x" /> is the length of the shortest program that prints <Math math="x" /> (and then terminates). 

There is an awkward problem with the above definition—what programming language do we use? Python? C? Assembly? Turing machine? Do we allow languages _and_ libraries? Printing a million digits of <Math math="\pi" /> can then reduce to this:

```
import sympy
print(sympy.N(sympy.pi, 1000000))
```

The important insight is that, at least if we stay on the theoretical side of things, the choice does not matter that much. The trick is that in any ([Turing-complete](https://en.wikipedia.org/wiki/Turing_completeness)) programming language, we can build an [interpreter](https://en.wikipedia.org/wiki/Interpreter_(computing)) of any other programming language. 
An interpreter is a program that reads code written in some other language, and executes its instructions. 

In any reasonable programming language, you can write an interpreter for any other reasonable language in at most, say, 1MB. But this means that Kolmogorov complexity of any object is fixed 'up to 1MB': If you have a 100MB Python script that prints the file, then you have a 101MB C, Assembly, Java, ... script printing the same file—just write code in which the first 1 MB is an interpreter of Python tasked to execute the remaining 100MB. 

So for large objects (like the 1GB Wikipedia file from Hutter's prize), there's nothing awkward in using Kolmogorov complexity. The flip side is that it's borderline meaningless to argue whether the Kolmogorov complexity of <Math math="\pi" /> is 200 or 300 bytes. That difference depends on the choice of programming language too much. <Footnote>The fact that talking about small Kolmogorov complexities is fishy won't stop us doing that in a minute. </Footnote>

</Expand>

<Expand headline = "How do we compute it? ">
The short answer: we don't—in fact, I am very, very certain that the answer to Hutter's challenge will never be known. 

The problem is that the shortest program printing 1GB of Wikipedia is going to be an absolute mess: If we ran it, it would start doing some absolutely incomprehensible stuff -- allocating tons of memory, rewriting it again and again,... until it would finally stop with the right output.<Footnote>Not really, the algorithm would finish a long time after the heat death of our universe. </Footnote>

More precisely, there are two issues. First, the number of potential candidate solutions to the challenge is exponentially large: Even if the answer to Hutter's riddle is just 10MB, we would still have to check <Math math="2^{10\,000\,000}" /> programs. 

Second—and worse—checking whether a given program solves Hutter's challenge is incredibly tough: we can't do better than run that program and hope that it terminates at some point. But even programs that do terminate can do so only after [some incredibly large number of steps](https://www.quantamagazine.org/busy-beaver-hunters-reach-numbers-that-overwhelm-ordinary-math-20250822/). 

The problem of computing Kolmogorov complexity is so badly hard that we literally call it uncomputable. 

<Expand advanced={true} headline = "Berry's paradox and uncomputability">
Here's a fun paradox known as [Berry's paradox](https://en.wikipedia.org/wiki/Berry_paradox). Consider the expression:

<Quote>
Let <Math math="n^*" /> be the smallest positive integer not definable in less than one hundred letters.
</Quote>

Presumably, there are only so many numbers you can define with sixty letters, so there should be the smallest 'undefinable' one—<Math math="n^*" />. But wait a minute, <Math math="n^*" /> is 'defined' by the sentence above! <Footnote>I often hear the following, more cheeky variant of Berry's paradox: I claim that all positive integers are interesting. Why? Well, consider the smallest noninteresting number. But this is a very interesting property! </Footnote>

What should we make of this? To understand a paradox properly, we have to slow down as much as possible and rephrase it as precisely as possible. Here, Kolmogorov complexity is the right language to do so. 

Here's the rephrasing. If you write positive integers in binary, you can see that talking about them is pretty much the same as talking about all binary strings. So let's talk about strings, not numbers. To formalize the part 'definable in less than a hundred letters', let's replace <Math math="60" /> by some number <Math math="C" /> and consider all those binary strings such that their Kolmogorov complexity is at most <Math math="C" />. In fact, let's call this set of strings <Math math="\text{Berry}(C)" />. 

Now, let's assume that there is an algorithm <Math math="A" /> that gets a string <Math math="x" /> as input and outputs its Kolmogorov complexity <Math math="K(x)" />. We can use <Math math="A" /> to perform the devilish plan of Berry: Imagine the lexicographically smallest string <Math math="x^*" /> that has <Math math="K(x^*) > C" />. This <Math math="x^*" /> is analogous to the integer <Math math="n^*" /> from the original paradox.<Footnote>Or the smallest boring integer from the joke. </Footnote>

On one hand, we have a simple algorithm <Math math="A'" /> that generates <Math math="x^*" />: Just generate all the strings in lexicographical order (<Math math="\mathsf{0}, \mathsf{1}, \mathsf{00}, \dots" />) and run <Math math="A" /> on each one. Stop once you find the first string where <Math math="A" /> returns more than <Math math="C" />. 

On the other hand, we defined <Math math="x^*" /> by <Math math="K(x^*) > C" />. If we choose <Math math="C" /> to be large enough, the two conditions <Math math="K(x^*) > C" /> and <Math math="K(x^*) \le |A'|" /> are in contradiction. 

We can now see where the problem lies. We made one tiny assumption: the existence of an algorithm <Math math="A" /> computing Kolmogorov complexity. So, this assumption must be wrong, there is unfortunately no such algorithm! <Footnote>This result is closely related to [halting problem](https://en.wikipedia.org/wiki/Halting_problem) and [Gödel's incompleteness theorems](https://en.wikipedia.org/wiki/G%C3%B6del%27s_incompleteness_theorems), see e.g. [this book](https://users.math.cas.cz/~pudlak/preface_toc.pdf). </Footnote>
</Expand>

</Expand>

## Kolmogorov vs entropy: <Math math="E[K(x)] \approx H(X)" /> 

Both Kolmogorov complexity and entropy try to measure something very similar: complexity, information, compression limit. Naturally, they are closely connected! It's a bit hard to see this on the first glance though: Entropy talks about probabilities, and their logarithms. Kolmogorov complexity talks about computer programs and their length. 

The connection goes like this: If you have a reasonable distribution (<Math math="X" />) over bit strings and you sample from it (<Math math="x" />), then the entropy of the distribution is roughly equal to the expected Kolmogorov complexity of the sample. I.e., <Math displayMode={true} math = "E[K(x)] \approx H(X)."/>

<Block headline = "Example: uniform distribution">
Flip a fair coin <Math math="n" /> times. The result is a uniform distribution over <Math math="2^n" /> binary strings of length <Math math="n" />. The entropy of this distribution is <Math math="n" />. Now let's examine the Kolmogorov complexity of a random $n$-bit string. 

On one hand, the Kolmogorov complexity of _any_ <Math math="n" />-bit string is at most <Math displayMode={true} math = "K(\underbrace{\textsf{01000\dots 010110}}_{\textrm{n bits}}) \le n + \textrm{something small}." /> That's because in any (reasonable) language, you can just print the string:

```
print('01000...010110')
```

But can the Kolmogorov complexity of an $n$-bit string be much smaller than <Math math="n" />? Sure -- notice that our uniform distribution contains many strings with very small Kolmogorov complexity, like the string <Math math="000\dots 0" />. However, those highly compressible strings don't really matter on average, and the reason is [coding theory](/08-coding_theory). 

Let's construct a concrete code that assigns a code name to each $n$-bit string in our distribution. For any string $x$, its code name is the shortest program that prints it.
{/* <Footnote>There is a subtlety here that you will hardly appreciate. Any Code has to be prefix-free: If <Math math="\mathsf{0}" /> is a code, then <Math math = "\mathsf{01}"/> can't be a code. So, to interpret a program as a code name, our programming language has to be prefix-free -- no program can be a prefix of another program. This can be done e.g. by appending a [null-character at the end of the string](https://en.wikipedia.org/wiki/Null-terminated_string), or writing its length at the beginning. </Footnote> */}
The average length of this code is exactly <Math math="E[K(x)]" />. But [we have seen](/08-coding_theory#source-coding) that any code has its average length at least as large as the entropy. Hence, <Math math="E[K(x)] \ge H(X) = n" />. We conclude that <Math displayMode={false} math = "E[K(x)] \approx H(X)"/>. 
</Block>

If you look at the above example, you can notice that we did not really use that the distribution is uniform, it works pretty much for any distribution.<Footnote>There is an annoying detail. The distribution _itself_ can be hard to describe in the sense of having large Kolmogorov complexity. See e.g. 14.3 in [Elements of Information theory](http://staff.ustc.edu.cn/~cgong821/Wiley.Interscience.Elements.of.Information.Theory.Jul.2006.eBook-DDU.pdf). </Footnote> I.e., you can think of the relation between the two as **The entropy is the average Kolmogorov complexity**. 

The case of a uniform distribution is the most interesting one: it tells us that most <Math math="n" />-bit strings can't really be compressed, since their Kolmogorov complexity is close to <Math math="n" />. In fact, <Math math="n" />-bit strings with Kolmogorov complexity <Math math="\ge n" /> are called _Kolmogorov random_, to highlight the insight that __bits are random if we can't compress them__.

Kolmogorov didn’t just lecture; he walked. Students remember “seminars” that were actually 40km day‑long hikes -- chatting about mathematics the whole way and then ending with dinner at the dacha.

Before those walks made him legendary as a mentor, his results made him a legendary researcher. One of his famous contributions is his axiomatization of probability from the 1930's -- It was only then that probability became a rigorous part of mathematics, on the same footing as mathematical analysis. The axioms tell you how probabilities must behave; but they don’t give that much of an intuition for what probability actually _is_, where it is coming from, how to think about it. 

In the 1960s, Kolmogorov turned to that question. His ingenius idea was to use the language of algorithms and computer science: Call an object simple if it has a short description (small Kolmogorov complexity); call it random when no description is much shorter than the object itself. In his shorthand: **random = incompressible**.


<Expand advanced={true} headline = "What is randomness?"> 


When [Solomonoff](https://en.wikipedia.org/wiki/Ray_Solomonoff) and [Kolmogorov](https://en.wikipedia.org/wiki/Andrey_Kolmogorov) developed Kolmogorov complexity,<Footnote>Even though 'Kolmogorov complexity' stuck, Solomonoff was first by a couple of years. We are talking ~1960s.</Footnote> they came from a similar angle. At the heart of the matter, probability is not about whether our world is governed by deterministic Newtonian laws, or what’s your favorite interpretation of quantum physics. It’s about modelling unpredictability. 

This intuition is extremely helpful in computer science. Algorithms frequently want to work with random bits — but how do we get them fast? In practice, we typically use a [_pseudorandom generator_](https://en.wikipedia.org/wiki/Pseudorandom_generator): we ask the operating system for a [_seed_](https://en.wikipedia.org/wiki/Random_seed) of perhaps 64 “truly random” bits (e.g., from hardware sensors). The pseudorandom generator is then a short piece of code that takes those 64 bits as input and repeatedly applies obscure mathematical operations to generate many more **random‑looking** bits. 

How do we even talk about those pseudorandom bits? As they are a deterministic function of the initial seed, they are not random at all from the perspective of classical probability theory. However, with Kolmogorov complexity, we can generalize “a string is random if we can’t compress it” to: **a string looks random to an algorithm \(A\) if \(A\) can’t compress it**. 

A bit more concretely: for a pseudorandom generator, we test whether it **fools** certain statistical tests, meaning the test can’t reliably distinguish whether the input is truly random or comes from the generator. The string is then _pseudorandom_ for such a fooled test — the test can’t find patterns it could use to compress it.   

You can try this in the widget below. It implements four simple \(k\)-mer statistical tests — based on counting frequencies of \(k\) consecutive flips for \(k\in\{1,2,3,4\}\). Let’s see how long you can flip coins before the \(k=4\) test flags you — getting to 100 flips is not so easy!

If a test flags your sequence of \(n\) flips as nonrandom, it means some patterns are too rare / too frequent, and the test could in principle compress your \(n\) flips to fewer than \(n\) bits. 

<CoinFlipRandomnessWidget />

Here are examples of how pseudorandomness helps us think about all kinds of stuff:

- [Mathematicians believe](https://en.wikipedia.org/wiki/Normal_number) that the digits of <Math math="\pi" /> fool all fixed \(k\)-mer counting tests. But digits of <Math math="\pi" /> are not a very good pseudorandom generator: an algorithm that “tests against <Math math="\pi" />” is not fooled. 
- Typical pseudorandom generators fool all kinds of basic statistical tests.<Footnote>See e.g. Chapter 3 in [TAOCP](https://en.wikipedia.org/wiki/The_Art_of_Computer_Programming).</Footnote> These sequences thus look random to those tests. But they fail to look random to algorithms that can use exponential time (such algorithms can brute‑force all the seeds). 
- In cryptography theory, we like to assume there are cryptographically secure pseudorandom generators that fool all statistical tests running in polynomial time. We don’t know whether such generators exist, but we have practical implementations that fool all known reasonably fast tests. 
- The classic [overhand shuffle](https://en.wikipedia.org/wiki/Shuffling) sucks and is not used in casinos. But if no player is trying to take advantage of it, the game being played typically looks the same as if the cards were shuffled properly.  
- Is a coin flip really random or not? With precise measuring apparatus, you could predict the result by measuring the coin as it is being flipped. Without it, you can’t. Thus, the result of the coin flip can be called random (unless you have the apparatus). 
- In general, when people discuss “what is probability,” they often end up at quantum‑physics interpretations. I prefer a down‑to‑earth view: **Randomness is a limit of pseudorandomness** — we say a bit sequence is random when we can safely disregard the existence of any feasible algorithm that could predict or compress it.

<Expand advanced={true} headline="Long runs">
Think of a long <Math math="n" />-bit string generated by flipping a fair coin <Math math="n" /> times. What is the longest consecutive run of zeros in such a string? You can use classical tools of probability theory like [Chernoff's inequality](https://en.wikipedia.org/wiki/Chernoff_bound) to compute that with high probability, the string won't contain runs of length more than <Math math="O(\log n)" />. 

But there's also a more direct way to see this: If a bit string <Math math="s" /> contains a large run of zeros of length <Math math="k" />, i.e., 
<Math displayMode={true} math = "s = s_1 \underbrace{00\dots 0}_{k} s_2"/>

you can **compress** it: Instead of storing <Math math="s" />, it suffices to store <Math math="s_1, s_2, k" /> in your memory. We need <Math math="\log n" /> bits to store the value of <Math math="k" />, so all in all, we can store <Math math="s" /> with only something like <Math math="|s_1| + |s_2| + O(\log n) = n - k + O(\log n)" /> bits. 

In other words, the Kolmogorov complexity of a string containing a run of <Math math="k" /> zeros is 
<Math displayMode={true} math = "K(x) \le n - k + O(\log n)." />
If it was often the case that a random string contains a substring of zeros of length <Math math="> C\log n" /> (for some suitable constant <Math math="C" /> that I did not bother computing and hid it inside <Math math="O()" />), we could use above trick to compress random strings. But that's not possible as we saw above. Hence, random strings typically can't have long runs of zeros. 

The true power of this view is that we can now understand why random strings can't have any long interesting patterns in them. If there were patterns, they would be predictable, and hence the strings compressible. But <Math math="E[K(x)] \ge H(X) = n" /> says that this can't happen. 
</Expand>

In the summer of 1956, John McCarthy invited a small group to Dartmouth to think about the so-called "Artificial Intelligence"—the legendary [Dartmouth workshop](https://en.wikipedia.org/wiki/Dartmouth_workshop). A bunch of people visited, but only three of them stayed the whole time: McCarthy, Marvin Minsky, and Ray Solomonoff. <Footnote>It's Solomonoff's notes that give us a fairly precise idea of what happened in that workshop. </Footnote> Solomonoff brought a memo about an "inductive inference machine," then kept worrying the same question for years: how should we weigh competing hypotheses? A few years later, this led him to the invention of Kolmogorov complexity (around the same time as Kolmogorov), as well as the Solomonoff prior that shows up next. 
</Expand>





Let's finish this minicourse where we started—with our Bayesian detective. 

Bayes' rule and derived formulas like KL divergence are great to understand what's happening as we are getting more and more evidence. Yet, there's a big elephant in the room here—how should the detective set up her prior probabilities? 

Solomonoff induction is the right answer to this question. It says: 
<Quote>
A hypothesis <Math math="h" /> should start with probability proportional to <Math math="2^{-K(h)}" />. 
</Quote>

The formula shouldn't feel so shocking. After all, we spent an [entire chapter](04-max_entropy) arguing that if you care about <Math math="f(x)" />, the natural distributions look like <Math math="p(x) \propto 2^{\lambda \cdot f(x)}" />. 

### A fishy situation

Let's see this on an example. This time, our Bayesian detective isn't flipping a coin, but she has a black box with a button -- each press gives back one bit (a red or a blue chip), possibly correlated with the past outputs of the box.  

Our detective pressed the button ten times and this is what she sees: 

<SolomonoffMiniWidget />

What now? You can notice that our detective is now in an opposite situation to [the first chapter](01-kl_intro). In that chapter, she started with a fixed prior and we just focused on the evolution of that prior as she was getting evidence. 

Now, she has the data and has to come up with some hypotheses and their priors. This is the situation that we find ourselves in much more often than the first-chapter situation. It's also much more dangerous: this is where we can fall into the trap of _overfitting_ (discussed later). 

Solomonoff gives the detective the following advice for what to do in our situation: just start with all possible hypotheses you can imagine and give each hypothesis <Math math="h" /> a prior proportional to <Math math="2^{-K(h)}" />. Then compute the posterior. 

In theory, this is an extremely appealing approach, and pretty much the answer for how to do statistics, if you ask me. In practice, there are two problems with this: First, we can't work with infinitely many hypotheses. Second, we can't compute their Kolmogorov complexity. 

### Computing priors

This sounds pretty bad but it's not the end of the world. To overcome the first problem, our detective may simply come up with a few plausible hypotheses after she sees the data. Most hypotheses have probabilities close to zero anyway. 

Here are four of them: 

- <Math math="\mathsf{Uniform}" />: Each dot is 50/50 red or blue, independently
- <Math math="\mathsf{Biased}" />: Each dot is independently red with 60% probability
- <Math math="\mathsf{Alternating}" />: The sequence alternates red and blue—each time there's 10% probability of the other color, though.  
- <Math math="\mathsf{Blocky(5)}" />: The sequence alternates blocks of length five that are either "mostly red" (2/3 red probability) or "mostly blue" (2/3 blue probability)

The second problem is that we can't compute Kolmogorov complexity; and it's not even well-defined unless we fix some programming language. That's also not necessarily that bad. We can often get some reasonable approximation. Let me try to do it here: 

- <Math math="\mathsf{Uniform}" />: I give this one zero bits of penalty, i.e., <Math math="K(\mathsf{uniform}) = 0" />. This looks weird since all programs that generate this hypothesis as their output have to spend at least a few bits to do stuff like "print(0.5)". But this kind of constant overhead is the same for all four hypothesis and adding a constant to all log-priors does not change anything, so we might as well forget this and give 0 penalty to the simplest hypothesis—this one.  
- <Math math="\mathsf{Biased}" />: The difference between this and the previous hypothesis is that now we have to specify a number—0.6. If you asked me to start listing different numbers between 0 and 1 in order of how "simple" they are, I would probably list 0.6 somewhere around 20-50th place, so let me give this hypothesis a penalty of <Math math="K(\mathsf{biased})\approx 5" />. 
- <Math math="\mathsf{Alternating}" />: This hypothesis is more complicated than treating each dot independently, but we still have only two types of dots. I give this penalty of 3 bits since I can think of a bunch of different mechanisms roughly as simple as this one, even if this one is among the simplest. The number 0.9 seems roughly as "simple" as 0.6 to me, so I give it 5 bits. In total: <Math math="K(\mathsf{alternating}) \approx 8" />. 
- <Math math="\mathsf{Blocky(5)}" />: This one seems the most complicated. I give 3 bits for alterations, and additional 3-4 more bits for the blocks having length 5. Finally, the number <Math math="2/3" /> is actually pretty simple, so <Math math="2-3" /> bits for that. In total: <Math math="K(\mathsf{blocky(5)}) \approx 9" />.

### Some observations: 
- If you compare <Math math="\mathsf{uniform}" /> and <Math math="\mathsf{biased}" /> hypotheses, they both have almost the same likelihoods (-10 vs -9.71 bits). Seeing 10 data points is simply not enough to start making meaningful inferences about whether the bias is 50%, or only "close to 50% but not quite". 
- <Math math="\mathsf{Alternating}" /> hypothesis is making very strong predictions. Since it matches the data pretty well, it hence accumulated a lot of evidence in its favor. With just 10 data points, the evidence is roughly offset by its complexity. But if we generate a few more data points from either <Math math="\mathsf{uniform}" /> or <Math math="\mathsf{alternating}" /> distribution, the hypothesis quickly gets to the top, or to the bottom. 
- The <Math math="\mathsf{half\text{-}half}" /> hypothesis looks a lot like [overfitting](https://en.wikipedia.org/wiki/Overfitting)<Footnote>Overfitting is a term used mostly by the machine-learning community. In statistics, people rather talk about [p-hacking and data dredging](https://en.wikipedia.org/wiki/Data_dredging). That term is a bit more general and includes variations on overfitting, as well as other vices like simply lying about your data. </Footnote>: We got a modest improvement at evidence at the cost of a large complexity of the hypothesis.

The following widget shows a simple machine-learning experiment -- we try to fit a bunch of points with polynomials of degree $k = 1, 2, \dots$ The question is: what is the best $k$? 

Remember, if we have a probabilistic model, we can interpret the loss (here: mean squared error) of the $k$-th model as the logarithm of the evidence going for it. So, naively (i.e., using the maximum likelihood principle), we should pick the model with the smallest loss. Of course, the loss goes down as we increase $k$, so MLE naively suggests to simply take $k$ as large as possible. 

Solomonoff prior is the ultimate theoretical answer to this: A polynomial of degree $k$ has $k+1$ parameters, so it should incur a penalty of size $\sim k$. I think that this is a powerful intuition for selecting the best model, though similarly to our above example: the devil lies in the details; especially: how many bits does each parameter have? 

In practice, there are two popular options to choose the right $k$ called [AIC](https://en.wikipedia.org/wiki/Akaike_information_criterion) and [BIC](https://en.wikipedia.org/wiki/Bayesian_information_criterion). Both of them are derived by much more technical arguments than our compression philosophising. Yet, they both agree that the penalty should be $k$-ish. The penalty of AIC is $2k$ bits<Footnote>It's more subtle for $k \approx n$, we use [AICc](https://en.wikipedia.org/wiki/Akaike_information_criterion#Modification_for_small_sample_size) correction in the widget below</Footnote> and the penalty of BIC is $k \cdot \log n$ bits. <Footnote>That is, you can view one technique as treating each parameter as a constant, while the other says that for $n$-sized inputs, parameters are $\log n$-bit-sized numbers.  </Footnote>

### Intuition

Why is Solomonoff prior the right one? There are some more complicated and rigorous justifications, but here's how I think about this. 

Let's think of an experiment where our Bayesian detective samples $n$ samples from an unknown distribution $p$; we have different models $q_1, \dots, q_k$. Solomonoff prior of $q_i$ is $2^{-K(q_i)}$ and the evidence going for that model is $2^{-H(p, q_i)}$.   

First, remember: under Solomonoff prior, a hypothesis $q$ has prior $2^{-K(q)}$ and if the data are $p$, the evidence for $q$ is $2^{-H(p,q)}$. So, choosing the most likely hypothesis means choosing the $q$ that minimize $K(q) + n \cdot H(p,q)$. 

But we know what that formula means! $K(q)$ is how many bits of memory we need to store the model $q$, and $n \cdot H(p,q)$ is how many bits of memory we need to store $p$, once we know $q$. <Footnote>Cf. our discussion on the Wikipedia riddle where we compared different compression algorithms ($q$) by how well they compress Wikipedia ($p$), where the length of the compressed file is $K(q) + H(p,q)$. Except for LLMs, the compression algorithms were so simple that $K(q)$ did not play much of a role, so we mostly just compared cross-entropies. </Footnote>

That is, using Solomonoff prior means that we are simply supposed to **prefer the models that compress the data the most**. This is also called optimizing [Minimum description length](https://en.wikipedia.org/wiki/Minimum_description_length) (MDL).

Imagine a special case of Solomonoff induction where each observation is either predicted by the model (likelihood = 1) or is not (likelihood = 0). Then Solomonoff induction is just crossing out models incompatible with the data. The posterior distribution over the non‑crossed‑out models is essentially the Solomonoff prior restricted there: each hypothesis <Math math="q" /> has probability proportional to <Math math="2^{-K(q)}" />. This neatly combines [Occam’s razor](https://en.wikipedia.org/wiki/Occam%27s_razor) (prefer simple hypotheses) with [Epicurus’ principle](https://en.wikipedia.org/wiki/Epicurus#Principle_of_Multiple_Explanations) (if multiple hypotheses explain the data, don’t discard any of them). 

Years later, an Enlightenment philosopher [David Hume](https://en.wikipedia.org/wiki/David_Hume) struggled with [the problem of induction](https://en.wikipedia.org/wiki/Problem_of_induction). Basically: even if we solve physics and find a perfectly good model <Math math="q" /> that fits everything so far, what about a model <Math math="q'" /> that is the same as <Math math="q" /> until tomorrow, but does some stupid rubbish afterwards? Hume, an empiricist, held that there’s no good rational justification for preferring <Math math="q" /> over <Math math="q'" />. But Solomonoff induction is a pretty good “rational” answer, if you ask me!<Footnote>Of course, whether this is satisfying depends on how we justified using the Solomonoff prior in the first place. I kind of pulled it out of a hat, but there are [nice](http://www.vetta.org/documents/Machine_Super_Intelligence.pdf) [theorems](https://link.springer.com/book/10.1007/978-0-387-49820-1) showing that it’s, in a sense, a unique probability distribution.</Footnote> If you use that prior, you get Occam’s razor: even if both hypotheses fit the data, the simpler one — <Math math="q" /> — is much more probable.
